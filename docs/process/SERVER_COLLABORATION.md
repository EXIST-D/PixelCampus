# 服务端协作指南：别人怎么改服务端（新功能 / 新字段）

> 前提（见 [ADR 0001](../adr/0001-public-private-split.md)、[ADR 0012](../adr/0012-server-private-repo.md)）：服务端不在公开仓库里，而是在独立的私有仓库 `PixelCampus-server`。本文说明**别人想参与带服务端的功能时怎么做**，以及改服务端代码和存档字段时必须遵守的规则。

## 一、三种协作方式（按信任程度）

### A. 默认：协作者只改公开仓库，服务端那一半由主人实现（推荐大多数人）
1. 先写 `docs/feature/<日期-名称>/spec.md`（需求）→ 主人确认 → 再写 `plan.md`（计划，里面写清**协议改动和存档字段**）。
2. 在公开仓库里做：`src/shared/<功能>.ts`（规则写成**纯函数**，带单测）、`src/shared/protocol.ts`（新消息 + 注释）、客户端界面。
3. 把「服务端要做什么」写成清单放进 plan.md 或 PR 说明：新消息的处理流程（校验什么、改哪些档案字段、回什么消息）、每日上限 / 冷却 / 位置要求。因为规则已经在 `shared/` 里，**服务端 handler 很薄**：取档案 → 调用 shared 规则 → 落盘 → 回消息。
4. 主人合并 PR 后实现服务端 handler、联调、部署。协作者用 `?offline` 单机模式验证客户端部分。

### B. 受信任的服务端协作者：加入服务端私有仓库（已上线，需要主人邀请）
服务端在**独立的私有仓库 `PixelCampus-server`**（[ADR 0012](../adr/0012-server-private-repo.md)），只含服务端代码和服务端测试；**不含**正式环境部署脚本、服务器信息、敏感词词库原文、玩家数据。主人把协作者加为该仓库的协作者（**写权限**），之后：
1. 克隆公开仓库，再把服务端仓库克隆到它的 `server/` 目录（公开仓库已忽略 `server/`，不会误提交）；`npm ci` + `npm run assets`。安装与运行步骤见服务端仓库的 README。
2. 本地联调：`npm run server`（8787）+ `npm run dev`（5173，Vite 把 `/ws`、`/up`、`/img` 代理到 8787）；测试 `npx vitest run`（公开 + 服务端测试一起跑）。
3. 在服务端仓库**开分支 + 提 PR**（`feature/xxx`、`fix/xxx`），不要直接推 `main`——免费版私有仓库没法强制保护 `main`，靠约定；主人只会 pull 审阅过的提交，线上部署用的是主人本机的代码，所以别人推 `main` 不会直接影响线上。
4. 共享规则 / 客户端 / 文档部分在**公开仓库**提 PR；两个 PR 互相链接。服务端 PR 描述里写一行 `Public-Branch: <用户名>/PixelCampus@<分支>`，服务端仓库的 CI 会拉那个公开分支和服务端一起跑类型检查与全部测试（不写就测公开 `main`）。
5. **主人审阅 → 合并两个 PR → 部署正式环境**（主人，或主人授权的协作者，见第五节与 [ADR 0013](../adr/0013-collaborator-prod-deploy.md)）。合并不会自动上线。
6. 局限：能看到代码就能复制，只能靠信任和约定；多人同时改要协调；协作者只能在测试环境验证，不能碰正式环境。

### C. 开放一个最小可运行的参考服务端（暂不推荐）
把服务端的接口 + 空实现放进公开仓库，让任何人能完整跑通联机。代价是要长期维护一份「去掉规则细节」的版本，且会暴露协议之外的服务端行为，目前不做。

## 二、改服务端 / 加字段必须遵守的规则

### 1. 存档字段（玩家档案 `Saved`）
- **新字段一律可选**；在 `src/shared/<功能>.ts` 写 `cleanXxx(raw)`（校验类型、截断长度、丢弃非法值），读档时过一遍：旧档案缺字段、被篡改的值都不会报错。
- **默认值不落盘**（没动过的玩家不占空间）；字段名尽量短——档案有上万份，每份在内存里约 2~8KB，新增字段要估算体积（写进 spec 的「性能与成本」）。
- **不改已有字段的含义**。必须改时：加版本标记（如 `v`）、读取时升级、用「老档案样本」写迁移测试；上线前用线上完整备份跑一遍重放（主人做）。
- 新的数据文件（如 `place.jsonl`）要写进 plan 的「备份清单」，并在 FEATURES / CHANGELOG 注明。

### 2. 协议（`src/shared/protocol.ts`）
- 新消息加在联合类型里并**写一行注释**（它会成为 [PROTOCOL.md](../architecture/PROTOCOL.md) 的说明），然后 `npm run protocol:doc`（有测试检查）。
- **向后兼容**：新增可选字段、新增消息不需要改 `PROTOCOL_VERSION`；会让旧客户端出错的改动才升版本——升版本会让所有在线玩家被提示「客户端版本过旧，请刷新页面」，要在 plan 里写明。
- 服务端在对应的 `server/handlers/<功能>-handler.ts` 的 `register(d)` 里登记「消息类型 → 处理函数」（限流 `limit`、是否打断牵手 `breaks` 是登记时的标志位）；重复登记启动即报错。

### 3. 校验与安全（信任模型：客户端只上报「想做什么」）
- 位置、冷却、每日上限、权限、价格、概率全在服务端；玩家文字用 `cleanText` + 敏感词过滤；需要审核 / 举报的内容走现有的审核与举报流程；管理员操作写审计日志。
- 不得在客户端之外信任任何数值；不得把真实 IP、口令、令牌写进日志或回给客户端。

### 4. 测试
- 规则 → `tests/<功能>.test.ts`（公开，纯函数）；服务端集成 → 服务端仓库的 `tests/<功能>.test.ts`（克隆后在 `server/tests/`；真起服务器 + ws 客户端，仿 `place-board.test.ts`；这类测试只在有服务端的环境跑）。
- 提交前：`npx tsc --noEmit -p .` 和 `npx vitest run` 全过；改了协议要 `npm run protocol:doc`；改了钓鱼规则要 `npm run guide`。

### 5. 性能与成本
- 估算新增的 CPU / 内存 / 磁盘 / 带宽；全表扫描（遍历所有玩家档案）要说明频率和代价（冻结的档案会被临时解析）；列表要分页、有上限；图片 / 文件走流式、有总量上限。

### 6. 上线
- 改了 `src/shared/*` 必须**前后端一起部署**；部署前备份玩家数据；新增 nginx 路由 / 请求体大小等运维改动写在 plan 的「上线计划」，由主人执行；部署后看页面哈希、服务状态、`/healthz`、日志。

## 三、协作者清单（改动带服务端时，PR 说明里逐条确认）
- [ ] 有 spec + plan（含协议 / 字段 / 备份 / 上线说明）
- [ ] 新字段可选 + `clean` 函数 + 迁移 / 兼容说明
- [ ] 新消息有注释、`protocol:doc` 已更新、是否升 `PROTOCOL_VERSION`
- [ ] 服务端校验（位置 / 冷却 / 上限 / 权限 / 文字清洗）都有
- [ ] 测试（规则 + 服务端）全过，`tsc` 无报错
- [ ] 性能 / 内存 / 磁盘估算写了
- [ ] FEATURES / CHANGELOG 已更新

## 四、测试环境：协作者先在测试环境验证，主人确认后再上正式

> 测试环境已就绪（见 [staging-env](../feature/20261110-staging-env/spec.md) 和 [ADR 0010](../adr/0010-staging-environment.md)）：和正式环境**同一台服务器、同一个域名和 HTTPS**，但独立进程 / 数据目录 / 端口 / 管理员口令，访问地址是不公开的隐藏路径（地址只告诉需要的人，不写进任何公开文档）。

**可以。** 流程是「协作者 → 测试环境联测 → 主人确认 → 正式环境」，**正式环境的部署**：默认由主人做；主人也可以把部署权下放给受信任的协作者（[ADR 0013](../adr/0013-collaborator-prod-deploy.md)，受限账号 + 预备份 + 自动回滚 + 审计）：

1. 协作者在自己的分支改服务端 / 客户端，本地 `tsc` + 全部测试通过，向服务端私有仓库（以及涉及 `src/shared/*` 时的公开仓库）提 PR。
2. **部署到测试环境**——两种做法：
   - **现在就能用（主人代劳）**：主人 checkout 协作者的分支，运行 `npm run deploy:test`（一条命令，构建 → 同步 → 重启），然后把测试地址发给协作者联测。协作者不需要任何服务器权限。
   - **协作者自助部署（已上线）**：协作者把**自己的公钥**发给主人，主人加到服务器的受限账号（`add`）；之后协作者在自己机器上 `bash server/scripts/deploy-test.sh`（只传代码，几 MB）部署、`bash server/scripts/test-env.sh status | logs | rollback | reset` 管理。受限账号只能执行白名单命令，不能开 shell、不能转发端口、碰不到正式环境；测试进程在沙箱里（不能访问外网、看不到正式数据）；新版本起不来自动回滚；详见 [ADR 0011](../adr/0011-collaborator-self-deploy.md) 和 [spec / plan](../feature/20261110-staging-self-deploy/spec.md)。再往后可加 GitHub Actions 工作流，协作者推送 `staging/*` 分支就自动部署到测试环境。用一把**受限的部署密钥**（只能写测试应用目录、只能重启测试服务，不能碰正式环境、nginx、玩家数据；密钥存在 GitHub Secrets 里协作者看不到）。
3. 联测：电脑 + 手机多人登录测试环境，按 PR 里的验收清单逐条验证；字段 / 迁移类改动用**旧格式的样本档案**验证（测试环境默认空数据，不使用真实玩家档案）。
4. **主人确认**：看 PR（代码审核）+ 联测结果，满意后合并到 main。
5. **上线正式环境**：主人备份数据后 `npm run deploy`，按部署清单校验（页面哈希、服务状态、`/healthz`、日志）。

**注意事项**
- 测试环境是**共用的一个实例**：同一时间只部署一个分支，部署前先通知一声（后续工作流会加队列 / 锁）。
- 测试环境**看不到正式环境的数据**（独立用户、`InaccessiblePaths`），并且有资源上限（内存 200MB、最多 30 人）；它验证功能，**不验证大并发**。
- 隐藏路径就是访问口令：只发给需要的协作者；有人退出协作或怀疑泄露时，换一个新的随机路径（主人改部署配置与 nginx 即可）。
- 测试环境通过 ≠ 可以上线：仍要主人审核代码；涉及档案字段的改动，上线前主人会用线上备份做重放校验。

## 五、从设计到上线：完整流程与「什么放哪」

测试环境是用来**运行和联测**的，不是用来提交代码的；代码永远在 git 里。协作者可以设计新功能、开发新玩法，按下面走：

| 步骤 | 谁 | 做什么 | 放在哪 |
|---|---|---|---|
| 1 设计 | 协作者 | 写 `docs/feature/<日期-名称>/spec.md`（需求）→ 主人确认 → `plan.md`（计划）→ 主人确认 | 公开仓库（fork 里开分支，提 PR；只含文档，可以先提） |
| 2 开发 | 协作者 | 规则 / 协议 / 客户端写在 `src/shared`、`src/ui`、`src/scenes`…；服务端 handler / 存档字段写在 `server/` | 公开部分：**自己 fork 的公开仓库分支**；服务端部分：**服务端私有仓库的分支** |
| 3 联测 | 协作者 | `bash server/scripts/deploy-test.sh` 部署到测试环境，电脑 + 手机联测，对照 spec 的验收标准 | 测试环境（共用一个实例） |
| 4 提交 | 协作者 | 公开仓库 PR（代码 + 测试 + 文档 + FEATURES / CHANGELOG）+ 服务端仓库 PR，两个 PR 互相链接（`Public-Branch:` 一行） | 两个仓库各一个 PR（先提 Draft 也行） |
| 5 审阅 | 主人 | 审两个 PR；服务端仓库的 CI 会把两边一起跑类型检查与全部测试；必要时把协作者的分支部署到测试环境亲自看；涉及档案字段的用线上备份做重放校验 | GitHub + 主人本机 |
| 6 合并 | 主人 | 合并两个 PR（`src/shared/*` 与服务端必须一起合并、一起测、一起部署） | 公开仓库 main；服务端仓库 main |
| 7 上线 | **协作者（受信任）或主人** | 协作者：`bash server/scripts/deploy-prod.sh`（只部署已合并 main 的代码）；服务器自动预备份 → 安装 → 健康检查 → 失败自动回滚；部署后实际玩一下，有问题 `prod-env.sh rollback`。主人：照旧 `npm run deploy`，并随时看审计日志 | 正式环境 |

要点：
- **合并 ≠ 上线**：合并只是进入代码库，上线是单独的一步，由主人或被授权的协作者手动执行（[ADR 0013](../adr/0013-collaborator-prod-deploy.md)；Claude 只在主人明确说「部署」时才部署）。
- **开发期间可以把客户端 / 共享规则推到公开仓库**（自己 fork 的分支，提 Draft PR 让主人早点看）。**服务端代码只在服务端私有仓库里**，不要放进公开仓库、公开 PR / Issue、网盘公开链接；测试环境的地址、路径、服务器信息同样不要写进公开的提交 / PR / Issue。
- 主人本机的 `server/` 同样是这个仓库的克隆：主人审阅后 `git pull` 再部署；主人自己的服务端改动也走这个仓库。
- 另有一个主人个人的私有备份仓库，备份部署脚本、词库、私有文档等**不对协作者开放**的东西；协作者只接触服务端仓库。
