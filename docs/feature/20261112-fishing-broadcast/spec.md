# 钓鱼全服播报：稀有鱼 / 新纪录

> 状态：**已确认（2026-11-12）**
> 规范：[docs/feature/spec.md](../spec.md)
> 对应 Issue：（待填 / 无则留空，作者确认后由作者或我开）

## 0.0 作者拍板（2026-11-12）

- 门槛：**神话鱼（mythic）或「新纪录」（record）**，锁定，不含 legendary。
- 形式：**世界频道 + 顶部金色横幅**，播报**也进世界频道的聊天记录**（有历史、可举报撤回）。
- 暴露：名字 + 鱼名 + 稀有度，不含尺寸/重量。
- 识别方式：给 `chat` 消息加**显式标记**（`kind`），不用 `pid===0 && uid===0` 约定。

## 0. 已确认的设计（本轮问答）

| 项 | 结论 |
|---|---|
| 触发门槛 | **神话鱼（mythic）或「新纪录」（record）** 才全服播报；史诗及以下、普通纪录不播 |
| 播报形式 | ① 复用 `chat` 消息走**世界频道**（带钓鱼者名字，可被玩家关/静音）；② 同时屏幕顶部闪一条**金色横幅**（不看聊天也能注意到） |
| 暴露内容 | **名字 + 鱼名 + 稀有度**，不含尺寸 / 重量等隐私 |
| 范围 | 动 `src/shared/*`（协议 + 规则）+ 服务端广播 + 客户端展示；**必须两边同步部署** |

## 1. 背景与目标

现状：钓到鱼后，提示走 `net.system()`（自己的系统频道）或 `hud.banner()`（自己的横幅），**只有钓鱼者本人可见**。别人钓到神话鱼、破纪录，全服无人知晓。

而项目已有 7 档稀有度（`common → uncommon → rare → epic → legendary → mythic`）和高光事件（`record` 新纪录 / `isNew` 图鉴新种类 / `first` 神话鱼首次），这些「值得全校知道」的素材现在全被锁在个人频道里。

目标：

- 让「钓到神话鱼」和「破个人纪录」这两类**大事**全服可见，制造「世界频道忽然炸了」的社交高光。
- 复用已有的 `chat` / `world` 频道机制承载，**不新造一套广播系统**；钓鱼播报即广播系统的第一个真实内容源。
- 克制：只播最稀有的事件，避免刷屏。

## 2. 范围

### 本期做

- 协议：`fish_state` 的 `catch` 增加一个标记（或复用现有字段），让服务端知道「这条鱼要广播」，并在广播的 `chat` 消息里带上钓鱼者名字、鱼名、稀有度。
- 服务端：钓到 `mythic` 或 `record` 时，向 `world` 频道广播一条系统消息。
- 客户端：世界频道收到这条消息时，顶部闪金色横幅 + 音效（复用 `Hud.banner()` 扩展）。

### 本期不做（留待后续）

- 放开给普通玩家手动发全服广播（`say` 仍是站长专属）。
- 系统定时广播（整点报时等）。
- 把 `epic` / `legendary` 也纳入播报（如需放宽，作者一句话即可，规则集中在同一处）。

## 3. 详细设计

### 3.1 触发条件（规则侧，`src/shared/fishing.ts`）

新增一个纯函数，客户端与服务端共用，判断「这一钩要不要广播」：

```ts
// 是否值得全服广播：神话鱼，或破了该玩家的个人纪录
export function shouldBroadcastCatch(def: FishDef, record: boolean): boolean {
  return def.rarity === 'mythic' || record === true;
}
```

> 规则集中在 `shared` 一处，后续若想放宽到 `epic`/`legendary`，只改这一个函数 + 测试。

### 3.2 协议（`src/shared/protocol.ts`）

`fish_state` 的 `catch` 分支增加一个可选标记，服务端据此决定是否触发广播（或直接在广播消息里带上内容）。两种方案，**倾向方案 A**：

- **方案 A（推荐，改动最小）**：不扩 `fish_state`，服务端在判定 `shouldBroadcastCatch` 为真时，直接复用现有 `chat` 消息广播：

  ```ts
  // 服务端向 world 频道广播（复用 chat 的完整结构）
  { t: 'chat'; pid: 0; uid: 0; from: ''; hue: 0; text: '🎣 某某钓到神话·河工锦！'; ts: now; ch: 'world' }
  ```

  其中 `text` 由服务端按统一格式拼好，客户端只是渲染，不做任何判断。

- **方案 B**：给 `fish_state` 加 `broadcast?: boolean`，客户端收到后自己拼横幅。但「别人」的广播仍要走 `chat` 下发，等于两条路，不如 A 统一。

> 关键决策点（需作者拍板）：`chat` 的 `from` 字段带的是玩家**昵称**；神话鱼/破纪录是否也要在聊天气泡里显示，还是只出横幅、不占聊天记录。倾向：**都进世界频道**（有历史、可被举报/撤回，符合现有管理机制），横幅只是视觉强调。

### 3.3 服务端（私有库）

- 钓鱼结算处，拿到 `FishDef` 和 `record` 后调用 `shouldBroadcastCatch`。
- 为真时，向该玩家所在世界的 `world` 频道广播 `chat` 消息（格式见 3.2）。
- 无需新增存档字段、无老数据迁移。
- **广播文本格式**（建议，供作者定稿）：
  - 神话鱼：`🎣 某某钓到了神话·河工锦！`
  - 新纪录：`🎣 某某刷新了「鲫鱼」的个人纪录！`
  - 两者同时（神话鱼又是纪录）：`🎣 某某钓到了神话·河工锦，刷新个人纪录！`

### 3.4 客户端（`src/ui` + `src/scenes/world`）

- 世界频道收到这类消息时（可通过 `chat` 消息的 `pid === 0 && uid === 0` 且文本带 `🎣` 前缀识别，或协议加 `kind` 标记），顶部闪金色横幅 + `sfx()`。
- 复用 `Hud.banner()`，新增一个「播报」样式（金色、稍长停留），不改现有 `banner()` 行为。

## 4. 测试计划

- **规则测试**（`tests/fishing-broadcast.test.ts`，纯函数）：
  - `shouldBroadcastCatch` 对 `mythic` 恒真、对 `record` 恒真、对 `epic` 无纪录恒假、对 `common` 无纪录恒假。
- **客户端测试**（如可行）：世界频道收到播报消息时触发横幅、系统频道不触发。
- **浏览器验证**：`?offline` 单人模式下本地钓到神话鱼/破纪录，看横幅；联机环境（私有测试服）验证他人可见。
