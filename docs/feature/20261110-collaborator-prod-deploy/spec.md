## 1. 背景与目标
- **问题**：协作者已能自助部署测试环境，但上线正式环境仍要等主人。主人希望**受信任的协作者可以自己部署正式环境**（主人在评估过「他发起、主人批准」方案后选择了完全下放）。
- **目标**：协作者在受限账号上能部署 / 回滚 / 查看正式环境；同时尽量降低「一次坏部署毁掉线上」的风险：部署前自动预备份、失败自动回滚（含数据）、审计、限频。
- **非目标**：不给 root、shell；不给数据还原权（只有主人）；不改变「Claude 只在主人明确说部署时才部署」的约定。

## 2. 用户与场景
- 协作者：测试环境联测通过 → 主人审阅并合并 PR → 协作者 `deploy-prod.sh` 上线 → 实际玩一下确认；出问题 `rollback`。
- 主人：不必每次亲自部署；可随时看审计日志、用预备份还原数据、撤销协作者。

## 3. 功能需求
| 编号 | 需求 | 优先级 |
|---|---|---|
| R1 | 受限账号新增 `deploy-prod [code\|full]`、`status-prod`、`logs-prod`、`rollback-prod`；其他命令仍一律被拒 | P0 |
| R2 | 正式安装前自动预备份整个数据目录，备份放在**服务进程和协作者都碰不到**的 root 专属目录，保留最近 5 份 | P0 |
| R3 | 安装后健康检查（服务起来、`healthz` ok、**玩家档案数不能掉**）；失败自动回滚代码，档案数异常时连 `players.json(.log)` 一起还原 | P0 |
| R4 | 两次正式部署最短间隔 2 分钟（回滚除外）；同一时间只允许一个部署 | P0 |
| R5 | 全部操作写审计日志（谁、何时、做了什么、拒绝也记） | P0 |
| R6 | 协作者侧脚本默认只部署**已合并到主仓库 main** 的代码（两个仓库都检查），部署前要输入确认 | P1（客户端约定，非强制） |
| R7 | 数据还原、撤销协作者、改正式环境配置只有主人能做 | P0 |

## 4. 规则与数值
- 上传上限：压缩后 code 60MB / full 200MB；解压后 200MB / 500MB；预备份保留 5 份；回滚点保留 3 个。

## 5. 界面与交互
- `bash server/scripts/deploy-prod.sh [--full]`、`bash server/scripts/prod-env.sh status | logs | rollback`。

## 6. 数据与协议
- 无协议和存档变化。服务器新增：`/var/backups/pixelcampus-predeploy/`（root 700）、`/var/lib/pc-deploy-state/`、`/opt/pixelcampus/releases/`、sudoers 里 4 个 `prod-*` 动词。**不改正式服务单元和 nginx。**

## 7. 安全、隐私与内容
- **风险（主人已知情并接受）**：协作者部署的代码以正式服务身份运行，能读写全部玩家数据，也能读到日志里的玩家昵称；坏代码可能损坏数据。缓解：预备份（碰不到）、健康检查与自动回滚、限频、审计、撤销即失效；仍只给**受信任**的人。
- 受限账号仍然不能开 shell、转发端口、读正式数据目录；sudo 仍只能以固定参数运行控制脚本。

## 8. 性能与成本
- 每次部署多一份约 5MB 的预备份（压缩后），保留 5 份；部署时在线玩家会重连（与主人自己部署一样）。

## 9. 验收标准
- [x] A1：正式环境四个动词可用（只读的 status-prod / logs-prod 在线验证过）；其他命令被拒；
- [x] A2：恶意包 / 压缩炸弹 / 空上传 / 带生成资源的 code 包 / 未知参数在到达安装前就被拒；
- [x] A3：`prod-install` 逻辑演练（常量映射到测试实例，**未重启正式环境**）：正常安装、限频拒绝、坏版本自动回滚、档案数异常自动回滚并还原数据（写坏的 `players.json` 校验和与部署前一致）、手动回滚、状态、预备份目录权限 700、审计日志；
- [x] A4：sudo 只能运行固定动词，越权全部被拒；预备份目录协作者读不到；
- [ ] A5：协作者第一次真实部署正式环境后，主人复核页面、`healthz`、审计日志（**尚未发生**）。
