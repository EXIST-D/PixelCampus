## 1. 方案概述
在已有的受限账号（[ADR 0011](../../adr/0011-collaborator-self-deploy.md)）上增加正式环境的四个动词，复用同一套上传校验与锁；root 控制脚本 `pc-test-ctl` 按「目标」参数化（test / prod 两套路径常量），prod 的安装多出：限频、预备份、档案数健康检查、数据还原。主人选择了完全下放（而不是「发起 → 批准」），所以靠**自动备份、自动回滚、审计、限频**降低风险。

```
协作者 deploy-prod ─► pc-test-gate（校验上传包、加锁）─► sudo pc-test-ctl prod-install
                                       ├─ 限频（2 分钟）
                                       ├─ 预备份 → /var/backups/pixelcampus-predeploy/（root 700，保留 5 份）
                                       ├─ 备份当前代码（保留 3 个回滚点）→ 安装 → 重启 pixelcampus
                                       ├─ 健康检查（healthz ok + 档案数 ≥ 部署前 99%）
                                       └─ 失败：回滚代码；档案数异常再还原 players.json(.log) → 重启 → 审计日志
```

## 4. 测试计划
- 在线（真实受限账号 + 临时密钥，用后撤销）：只读动词、越权、恶意包、压缩炸弹、空上传、未知参数；
- 演练：把 prod 常量映射到**测试实例**，原样运行安装逻辑：正常安装、限频、坏版本回滚、档案数异常回滚并还原数据（坏版本把档案写坏，还原后校验和一致）、手动回滚、状态、备份目录权限、审计；
- **没有**真实重启正式环境（主人没要求部署）；第一次真实部署由协作者完成后复核（A5）。

## 5. 上线计划
- 一次性安装：`bash deploy/pcdeploy.sh install`（更新 gate / ctl / sudoers）；不改正式单元和 nginx；回滚：把 `pc-test-ctl` / `pc-test-gate` / sudoers 换回旧版本（私有仓库历史里有）。

## 6. 风险与应对
| 风险 | 影响 | 应对 |
|---|---|---|
| 协作者部署的代码损坏 / 泄露玩家数据 | 严重 | 预备份（root 专属）、自动回滚含数据、限频、审计；只给受信任的人；撤销即失效 |
| 健康检查没发现的逻辑错误 | 玩家体验受损 | `rollback-prod` 一条命令回退；协作者部署后要实际玩一下 |
| 部署时间不合适（玩家多） | 玩家重连 | 约定部署前通知主人、避开高峰（非强制） |
| 绕过客户端防呆（直接调受限命令） | 部署未审阅代码 | 靠约定与审计日志；这是信任问题，不是技术限制 |
