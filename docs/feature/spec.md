# 需求规格（spec）模板

> **这份文件是模板。** 每个新功能（或较大的调整）复制一份到 `docs/feature/<YYYYMMDD-功能名>/spec.md`，再按下面的栏目填写；同一目录里再放一份 [plan.md](plan.md)（计划）。
> 目录名示例：`docs/feature/20261110-place-board/`。已经做完的功能，spec 留着当需求档案。

## 开发流程（以后都按这个来）
1. **写 spec**（需求）→ 主人确认（改完再确认，状态改成「已确认」）。需求没确认之前不写代码。
2. **写 plan**（计划：拆任务、协议 / 数据改动、测试与部署方案）→ 主人确认。
3. **开发**：按 plan 的任务顺序做，每个任务单独提交（提交信息用中文），测试全过。
4. **收尾**：对照 spec 的「验收标准」逐条验证（没验证到的如实写明）→ 同步 `docs/FEATURES.md`、`docs/CHANGELOG.md`（标日期、是否已部署）→ 把 spec / plan 头部的状态改成「已完成 / 已部署」。
5. **部署**：只在主人明确说「部署」时做（备份 → deploy → 校验）；公开仓库只在主人说「推公开仓库」时推。

> **公开仓库**：`docs/feature/` 下的 spec 和 plan 都进公开仓库（协作者要靠它们理解需求、参与开发）。**所以不要在里面写**服务器地址 / IP、口令、令牌、玩家数据、内部运维细节——涉及这些的内容写到私有文档 `docs/private/` 里，这里只写到「需要部署 / 需要改 nginx」这一层。
