## 1. 方案比较
| | A. 独立机器（已有的悉尼备用机） | B. 正式服务器上再起一个实例 |
|---|---|---|
| 隔离 | **物理隔离**：改坏、跑满内存都不影响正式环境和同机其他服务 | 同机：共用 2 核 / 1.6GB 内存（已有其他服务），需要限制资源 |
| 资源 | 备用机 2 核 / 1.9GB、磁盘余量大；游戏已装好（旧版本） | 可用内存约 400~500MB，测试实例 ≤ 200MB 可行但紧 |
| 网络 | 悉尼，国内访问延迟较高，但测试够用；公网 IP 只开 HTTP | 与正式同域名 + 真实 HTTPS（手机联测最像线上） |
| 改动面 | 只改本机部署脚本参数 + 备用机上的配置 | 还要给正式服务器新增 systemd 单元、nginx 路径、数据目录（只新增，不改已有，需备份 + `nginx -t`） |
| 风险 | 低 | 中（nginx 重载、资源竞争） |
| 结论 | 备选 | **采用（主人 2026-11-10 拍板：要和线上同一张网的真实 HTTPS）** |

## 3. 协议与数据变更
- 无协议 / 存档字段变化。
- 新增：测试环境专用的数据目录、管理员口令文件；**不拷贝正式玩家档案**（含个人信息）。
- nginx：只在我们自己的 snippet 里**新增**隐藏路径的 location（先备份、`nginx -t` 通过再 reload，失败自动还原）；不改任何已有配置。

## 4. 测试计划
- 部署脚本：用 `DRY_RUN`（只打印目标与命令）核对正式 / 测试两个入口的目标；
- 联测：`deploy:test` 后桌面浏览器 + 手机各登录一个账号，互相可见、聊天、留言板传图、宿舍装修；
- 隔离：测试环境操作后检查正式环境 `healthz` 的 profiles 数与 `players.json` 不变；
- 访问控制：未授权请求返回 401 / 拒绝。

## 5. 上线计划
- 在正式服务器上**只新增**：测试用户 / 目录 / 服务 / nginx location；已有服务和正式环境不改。
- 回滚：停掉并禁用测试服务、删除新增的 nginx location（有备份）即可，不影响正式环境。

## 6. 风险与应对
| 风险 | 影响 | 应对 |
|---|---|---|
| 误把测试部署到正式（或反之） | 影响真实玩家 | 目标显式、输出醒目、正式部署保留现有的防呆与确认 |
| 测试环境被外人访问 | 泄露开发中的功能、占用资源 | 访问控制 + 资源上限 + 不放在公共链接里 |
| 同机资源竞争（内存 / CPU） | 影响正式环境 | 测试实例内存上限 200MB、最多 30 人、构建 / 上传避开高峰；部署后核对正式 `healthz` |
| 把真实数据拷进测试环境 | 隐私风险 | 默认空数据；需要样本用脱敏脚本 |
