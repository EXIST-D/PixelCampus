# 0013 受信任的协作者可以部署正式环境（带预备份、自动回滚、审计）

- 状态：已采纳（部分取代 [ADR 0008](0008-deploy-by-owner.md)：正式环境不再只由主人部署）
- 日期：2026-11-10

## 背景
协作者已能自助部署测试环境（[ADR 0011](0011-collaborator-self-deploy.md)），但上线正式环境仍要等主人。主人评估了三种方式：A 主人部署、B 协作者发起主人批准、C 完全由协作者部署，**选择了 C**，并已被告知风险：协作者部署的代码以正式服务身份运行，能读写全部玩家数据。

## 决定
- 受限账号新增正式环境动词：`deploy-prod [code|full]`、`status-prod`、`logs-prod`、`rollback-prod`；仍不给 root / shell；数据还原、撤销协作者、改配置只有主人；
- 正式安装的保护：**预备份**整个数据目录（root 专属目录，服务进程与协作者都碰不到，保留 5 份）→ 安装 → **健康检查**（服务起来、`healthz` ok、玩家档案数不低于部署前 99%）→ 失败**自动回滚**（档案数异常再还原 `players.json(.log)`）→ **审计日志** → **限频**（2 分钟）；
- 协作者侧脚本默认只部署**已合并到主仓库 main** 的代码，并要求输入确认；这是约定与防呆，不是硬性技术限制；
- 「Claude 只在主人明确说『部署』时才部署」的约定不变。

## 后果
- 上线不再依赖主人，但风险转移到协作者与流程：只给受信任的人，部署前后要沟通、实际验证；
- 绕过客户端防呆直接调用受限命令仍可部署未合并的代码——靠信任和审计日志约束；
- 正式环境部署的日志可能含玩家昵称，协作者能看到；
- 撤销协作者（删公钥）即失效。

## 备选方案
- B 协作者发起、主人批准（更安全，被主人否决）；A 仍由主人部署（最安全，但慢）。
